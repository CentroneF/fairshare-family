# FairShare Family — Domain Distillation

## Scope and evidence

This is a domain map, not a design proposal. It is based on the product PRD, shaping notes, roadmap, archived change plans, and the current source and database migrations. The PRD is available, so this analysis is not limited to inference from code. The primary product purpose is to reduce conflict by giving separated co-parents a reliable shared view of child spending and an agreed monthly settlement ([context/foundation/prd.md:18-26](../foundation/prd.md)).

### Context and implementation map

The application is an Astro 6, React 19, TypeScript, Tailwind, Supabase, and Cloudflare Workers web application ([README.md:7-14](../../README.md)); the selected stack records the same TypeScript/Cloudflare-first intent ([context/foundation/tech-stack.md:22-24](../foundation/tech-stack.md)). The business logic is split deliberately:

| Layer | Location | Responsibility observed |
| --- | --- | --- |
| UI / delivery | `src/pages/`, `src/components/` | Astro pages and dialogs/forms display reports and invoke API endpoints; e.g. the balance panel renders total, approved, and review amounts ([src/components/expenses/MonthlyBalancePanel.astro:48-60](../../src/components/expenses/MonthlyBalancePanel.astro)). |
| HTTP command boundary | `src/pages/api/` | Authenticated endpoints pass validated form data to domain-facing helpers/RPCs, e.g. expense creation calls `createExpense` ([src/pages/api/expenses/create.ts:18-31](../../src/pages/api/expenses/create.ts)). |
| Application/read services | `src/lib/` | Pure financial rules, input normalization, onboarding resolution, and Supabase read adapters; `deriveMonthlyBalance` is the calculation seam ([src/lib/financial-rules.ts:36-89](../../src/lib/financial-rules.ts)). |
| Authoritative write model and persistence | `supabase/migrations/` | PostgreSQL tables, constraints, forced RLS, and `SECURITY DEFINER` command functions hold transaction/state authority; all domain tables use forced RLS ([supabase/migrations/20260717160000_financial_rules_foundation.sql:241-250](../../supabase/migrations/20260717160000_financial_rules_foundation.sql)). |
| Proof | `src/lib/*.test.ts`, `supabase/tests/` | Vitest covers pure rules; pgTAP covers access and transaction constraints. The test strategy identifies the database RPC layer—not UI—as the financial trust boundary ([context/changes/testing-expense-settlement-state-protections/research.md:26-30](../changes/testing-expense-settlement-state-protections/research.md)). |

## 2. Subdomain classification

Classification follows the vision’s conflict-reduction outcome and primary success criteria, not implementation size. The financial agreement is the product’s differentiator; authentication and generic application delivery are not.

| Area / concepts | Classification | Justification |
| --- | --- | --- |
| Shared expense review, 50/50 balance, monthly settlement, locking, payment snapshot | **Core** | These deliver the promised “reliable view” that removes monthly uncertainty ([context/foundation/prd.md:18-22](../foundation/prd.md)) and directly satisfy the primary criterion to record/review, determine balance, and jointly settle ([context/foundation/prd.md:28-32](../foundation/prd.md)). Financial accuracy and non-unilateral settlement are explicit guardrails ([context/foundation/prd.md:38-42](../foundation/prd.md)). |
| Family membership, children, join code, family-scoped visibility | **Supporting** | Necessary context, participant identity, and security boundary for the shared financial workflow, but not the product advantage by itself. The PRD frames these as setup/access requirements ([context/foundation/prd.md:68-75](../foundation/prd.md), [116-122](../foundation/prd.md)). |
| Current/historical report presentation and month navigation | **Supporting** | Enables the core decisions and is a primary criterion, but is a read/presentation surface over the expense and settlement model rather than the rule that makes those decisions correct ([context/foundation/prd.md:90-99](../foundation/prd.md)). |
| Accounts, email/password session, Supabase authentication | **Generic** | Commodity identity/session capability required by the product, with no domain-specific advantage; the stack intentionally supplies Supabase authentication ([README.md:75-77](../../README.md)). |
| Responsive PWA, Astro/React delivery, Cloudflare deployment | **Generic** | Platform and delivery concerns. They support access but do not change how co-parents determine or agree a settlement ([context/foundation/prd.md:101-106](../foundation/prd.md)). |
| Recurring monthly expenses | **Supporting (future)** | It is explicitly secondary/nice-to-have ([context/foundation/prd.md:34-36](../foundation/prd.md), [77-88](../foundation/prd.md)); fresh per-occurrence approval keeps it attached to the core review rule. |

## 3. Aggregate candidates and invariants

These are candidates for transactional consistency boundaries, inferred from the rules and command locks—not proposed production classes.

| Candidate | Invariant that must always hold | Source evidence | Enforcement status |
| --- | --- | --- | --- |
| **Family membership** | An account belongs to at most one family and a family has at most two active parent members. | “each account can belong to only one family” — [context/foundation/prd.md:68-71](../foundation/prd.md); “No families with more than two co-parents” — [context/foundation/prd.md:124-131](../foundation/prd.md) | **Enforced.** `UNIQUE (user_id)` ensures one membership ([supabase/migrations/20260717160000_financial_rules_foundation.sql:11-21](../../supabase/migrations/20260717160000_financial_rules_foundation.sql)); trigger serializes and rejects a third active parent ([143-173](../../supabase/migrations/20260717160000_financial_rules_foundation.sql)). |
| **Expense** | A valid expense has a positive two-decimal PLN amount; only the other active parent may review it; an edit returns it to pending/re-review. | “Creating or editing an expense requires approval from the other parent.” — [context/foundation/prd.md:116-120](../foundation/prd.md) | **Enforced.** SQL validates money/date and family/child ownership ([supabase/migrations/20260729170000_joint_monthly_settlement.sql:103-120](../../supabase/migrations/20260729170000_joint_monthly_settlement.sql)); review and re-review transitions are checked in SQL ([supabase/migrations/20260729180000_fix_settlement_review_commands.sql:11-31](../../supabase/migrations/20260729180000_fix_settlement_review_commands.sql), [supabase/migrations/20260729170000_joint_monthly_settlement.sql:225-246](../../supabase/migrations/20260729170000_joint_monthly_settlement.sql)). |
| **Monthly report / settlement** | A report can settle only for a past month with exactly two parents, at least one expense, all expenses approved, and two different parental confirmations. | “only when no pending or declined expenses remain” — [context/foundation/prd.md:98-99](../foundation/prd.md); “only with both parents' agreement” — [context/foundation/prd.md:120-122](../foundation/prd.md) | **Enforced, with a stricter implementation rule.** The confirmation RPC checks month, parent count, non-empty expenses, all-approved state, and a distinct second confirmer ([supabase/migrations/20260729170000_joint_monthly_settlement.sql:293-323](../../supabase/migrations/20260729170000_joint_monthly_settlement.sql)); database constraints require the confirmation pair for `settled` ([supabase/migrations/20260717160000_financial_rules_foundation.sql:84-101](../../supabase/migrations/20260717160000_financial_rules_foundation.sql)). |
| **Settled payment snapshot** | A settled record has internally consistent approved total, contributions, payment amount, and either no parties for zero payment or two distinct payment parties. | “Expense balances and monthly reports remain financially accurate.” — [context/foundation/prd.md:38-41](../foundation/prd.md) | **Enforced.** The snapshot constraint requires contributions to sum to approved amount and validates payment-party combinations ([supabase/migrations/20260729170000_joint_monthly_settlement.sql:53-85](../../supabase/migrations/20260729170000_joint_monthly_settlement.sql)). |
| **Family financial workspace** | A parent can see only the children, expenses, and reports of their own active family. | “Only authenticated accounts invited into a family can see that family's children, expenses, and reports.” — [context/foundation/prd.md:101-104](../foundation/prd.md) | **Enforced.** Forced RLS and select policies use `is_active_family_member` ([supabase/migrations/20260717160000_financial_rules_foundation.sql:200-215](../../supabase/migrations/20260717160000_financial_rules_foundation.sql), [241-277](../../supabase/migrations/20260717160000_financial_rules_foundation.sql)). |

## 4. Model versus code divergences

“Divergence” includes both gaps and intentional stricter/product-expanding behavior. It is not automatically a defect.

| Document model | Current code | Evidence / impact |
| --- | --- | --- |
| Recurring expenses are a secondary requirement with fresh approval per occurrence. | No recurrence entity, scheduling command, occurrence creation, or UI exists. | Requirement: [context/foundation/prd.md:77-88](../foundation/prd.md). The roadmap explicitly parks it: [context/foundation/roadmap.md:154-160](../foundation/roadmap.md). This is an acknowledged scope gap, not an accidental omission. |
| MVP has “no in-app expense dispute workflow” and “no comments on expenses.” | Declining requires and persists a 1–500-character `decline_reason`; the UI displays it and retains it as `previous_decline_reason` after correction. | Non-goals: [context/foundation/prd.md:124-129](../foundation/prd.md). Command evidence: [supabase/migrations/20260729180000_fix_settlement_review_commands.sql:37-73](../../supabase/migrations/20260729180000_fix_settlement_review_commands.sql); UI: [src/components/expenses/ExpenseList.astro:112-140](../../src/components/expenses/ExpenseList.astro). This is a narrow, one-way review explanation rather than a general discussion, but it contradicts the literal non-goal. |
| An expense may be edited/deleted while its report is “unsettled”; deletion is permitted when it was entered by its payer “without approval.” | Any first confirmation locks the month before it becomes `settled`; deletion is permitted only while `pending` or `declined`, not an approved expense. | Requirement: [context/foundation/prd.md:81-84](../foundation/prd.md). Code: lock on first confirmation ([supabase/migrations/20260729170000_joint_monthly_settlement.sql:237-246](../../supabase/migrations/20260729170000_joint_monthly_settlement.sql)); delete-state check ([251-275](../../supabase/migrations/20260729170000_joint_monthly_settlement.sql)). The lock is a protective refinement; the delete wording is made operational as “unapproved,” which excludes approved records. |
| Settlement eligibility requires a past report with no pending or declined expenses. | The code additionally requires at least one expense; an empty past month cannot be settled. | Requirement: [context/foundation/prd.md:98-99](../foundation/prd.md). Extra rule: [supabase/migrations/20260729170000_joint_monthly_settlement.sql:309-312](../../supabase/migrations/20260729170000_joint_monthly_settlement.sql). This is a product-policy addition that prevents recording “nothing to settle.” |
| The business language says a report is locked when settled. | Code introduces a separate first-confirmation “confirmation-locked” state, even though persistence status remains `open`. | PRD: [context/foundation/prd.md:120-122](../foundation/prd.md). UI language: [src/components/expenses/MonthlyBalancePanel.astro:93-103](../../src/components/expenses/MonthlyBalancePanel.astro); persistence state: [supabase/migrations/20260717160000_financial_rules_foundation.sql:65-101](../../supabase/migrations/20260717160000_financial_rules_foundation.sql). The model should name this intermediate business state explicitly to avoid treating `open` as mutable. |

## 5. Refactoring ranking

The ranking values business impact more than code size. “Risk” means the chance of invalid state if the aggregate’s protection is bypassed, weak, or split across boundaries today.

| Rank | Candidate | Core value | Current enforcement / risk | Why this position |
| --- | --- | --- | --- | --- |
| **1** | Monthly report / settlement | Highest: it turns raw costs into the mutually agreed outcome that prevents conflict. | Strong database protection, but its semantics span pure TypeScript calculation, multiple RPCs, snapshots, and an unnamed intermediate lock. **Medium risk.** | Refactor/domain-document first: make **Open → First-confirmed/locked → Settled** an explicit model with its eligibility and snapshot rules. This reduces ambiguity behind the most irreversible action. |
| 2 | Expense | Highest: the data feeding every balance and settlement. | Validation and transitions are strongly SQL-enforced, but lifecycle rules are repeated across update/delete/review commands. **Medium risk.** | Consolidate/document the lifecycle and correction transitions after settlement state is clarified. |
| 3 | Settled payment snapshot | High: auditability and final financial accuracy. | Constraint-backed snapshot; **low-to-medium risk** from duplicated TypeScript/SQL rounding and direction logic. | Keep the database snapshot authoritative and add equivalence tests whenever calculation rules change. |
| 4 | Family membership | Supporting but safety-critical. | Unique constraint, trigger, and RLS; **low risk**. | Preserve the existing boundary; no structural refactor is justified ahead of the core financial model. |
| 5 | Family financial workspace / authorization | Supporting and privacy-critical. | Forced RLS plus database tests; **low risk**. | Continue regression coverage rather than refactor. |

The first refactoring target is therefore the **monthly report / settlement aggregate**. Its rules are the product’s central promise, it has the highest cost of an invalid transition, and the current code uses a meaningful but under-specified intermediate “confirmation lock” that is not represented in the original ubiquitous language. The desired outcome is a clearer domain boundary and shared vocabulary, not a change to the established database authority.
